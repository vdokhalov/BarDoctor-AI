**Итог: найдены два воспроизводимых расхождения.** Основной поток POS/ручной продажи, складские количества, известная себестоимость, идемпотентность и откат транзакции прошли. Аудит в целом не имеет статуса PASS.

## Условия проверки

Все действия выполнены в новой SQLite `:memory:` через реальные route/auth/service modules, загруженные существующим `lifecycleRuntime`. Начальные остатки и подтверждённые стоимостные движения — синтетическая fixture. Месячный отчёт рассчитан фактическими функциями текущего клиентского bundle, включая его обёртки, через существующий `compileFinancialClient`. Ожидаемые суммы заданы независимо от production calculators.

Production endpoints, рабочие и production QA-заведения не использовались. Изменены только новый диагностический файл и этот отчёт; приложение, схема БД, секреты и production не менялись. Схема SQLite создаётся только внутри памяти теста.

## AUDIT-01 — складской импорт выпадает из себестоимости при смешанном учёте

Приоритет: высокий; завышение определённой как достоверная прибыли на проверенном сценарии.

Воспроизведение:

1. Провести live-продажу 1 Beer: выручка 20, расход 1 шт., стоимость 5 MDL.
2. Через `POST /api/sales-batches` импортировать текст `Beer 1` и провести полученный batch. Это отдельный складской расход, не связанный с первым event.
3. Оба движения реально уменьшают запас: 20 → 18 шт.; стоимость склада 300 → 290 MDL.
4. Сформировать месячный отчёт с известными граничными остатками 300 и 290 MDL.

| Показатель | Ожидание при включении обоих расходов | Факт |
|---|---:|---:|
| Выручка | 20 | 20 |
| Зафиксированная стоимость импортного batch | 5 | 5 |
| Себестоимость двух расходов | 10 | 5 |
| Валовая прибыль | 10 | 15 |
| Переоценка при неизменных ценах | 0 | −5 |

Безопасной альтернативой является явное указание неполного покрытия с неизвестной себестоимостью/прибылью, пока назначение импорта не разрешено. Текущий результат — известная прибыль 15 — такого ограничения не показывает.

Точная причина: `historicalPeriodCost` в `lib/bardoctor/financial-reconciliation.ts:197` собирает стоимость через строки выручки, связанные events и явно связанные sales documents. Самостоятельный активный импортный batch и его расходные движения не проверяются на полноту покрытия. `reconcileMonthlyReport` считает результат достоверным и относит разницу граничных остатков в `inventoryRevaluation` (строки 260 и 273).

Это не ошибка количества на складе и не основание добавлять импортную выручку по текущей цене меню. Нельзя исправлять её простым суммированием всех batches: импорт может пересекаться с уже отражёнными продажами. Нужен контроль происхождения и покрытия; при неразрешённой связи финансовый результат должен явно оставаться неполным.

## AUDIT-02 — отмена складской части подтверждённого отчёта оставляет выручку

Приоритет: высокий; переход в противоречивое состояние между документом, складом и финансовой проекцией.

Воспроизведение:

1. Через `POST /api/sales/confirm` подтвердить дневной отчёт: 1 Beer + 2 Coffee, выручка 50, себестоимость 6,60 MDL.
2. Получить его batch через реальный `GET /api/sales-batches`: он POSTED, содержит проведённые строки, не имеет readOnly, а capabilities.reverse разрешён.
3. Вызвать разрешённый `POST /api/sales-batches` с `action: reverse` для этого batch.
4. Ответ HTTP 200; склад возвращается к начальному состоянию.

| Показатель | Безопасный результат | Факт |
|---|---|---|
| Действие | Отклонено без записи либо согласованная отмена всех связанных сущностей | Складская отмена принята |
| Остатки после принятой полной отмены | 20 / 2 / 1 | 20 / 2 / 1 |
| Выручка при согласованной полной отмене | 0 | 50 MDL |
| Дневной документ | Больше не подтверждён как действующая продажа | Остаётся confirmed |
| Покрытие себестоимости | Согласованное | Неизвестное |
| Прибыль | 0 при полной отмене | null |

Точная причина: `/api/sales/confirm` создаёт связанные документ, batch, движения и выручку атомарно (`app/api/sales/confirm/route.ts:152`). Однако ветка reverse в `app/api/sales-batches/route.ts:417` обновляет только batch, ассортимент, движения и audit log; связь с подтверждённым финансовым документом не защищена. UI предлагает это действие по обычным условиям проведённого batch (`public/sales-import.js:332`).

Финансовый reader корректно перестаёт выдавать числовую прибыль при нарушенной связи. Проблема — в принятой частичной отмене. Минимальное безопасное направление исправления: серверный запрет отдельной складской отмены связанного подтверждённого отчёта до появления согласованного механизма отмены. Это не требует разрешать возвраты POS.

## Ограничения и следующий шаг

Проверка не является новым production smoke и не доказывает наличие этих комбинаций в реальных данных пользователя. UI не автоматизировался: доступность отмены подтверждена реальным API payload и условием действующего UI. Начальные данные и граничные снимки отчёта заданы fixture; полный процесс покупки/физической инвентаризации не был целью этого аудита. Полный build и вся тестовая матрица проекта не повторялись, поскольку исходный код приложения не изменён.

Рекомендуемый следующий этап: отдельное точечное исправление AUDIT-01/AUDIT-02, начиная с серверной защиты отмены связанного дневного отчёта. Затем определить безопасную политику неполного покрытия импортов, добавить обычные regression tests и прогнать полный release workflow. Исправления и deployment в рамках текущего аудита не выполнялись.
