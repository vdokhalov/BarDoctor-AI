# Автоматическая печать: этап 2, локально проверенная реализация

Реализовано в исходниках, не опубликовано и не установлено в заведении. Все ключи/коды из тестов относятся только к временным изолированным SQLite-базам.

## Обычная работа

Руководитель открывает в кассе «Действия администратора → Принтеры и очередь». Он создаёт код подключения, сопрягает один подготовленный Windows-компьютер, выбирает для подразделений меню зарегистрированные принтеры и запускает явный тест печати. После этого подтверждение новых позиций и отмена формируют существующие неизменяемые бегунки. Агент `watch` автоматически получает их, отправляет и возвращает статусы. Экспорт/импорт не нужен в обычной работе.

Экран показывает последнюю связь, активность доступа, очередь, неопределённые результаты и кнопку отзыва. Обновление списка — явной кнопкой «Обновить», без фонового таймера диалога. Отправленные в TCP/spooler задания не называются физически напечатанными. В истории заказа показывается маршрут, а состояние доставки — в очереди.

## Подготовка Windows после отдельного разрешения

Сначала выполнить требования к ОС, драйверу, профилю CP866, RAW-совместимости и локальной базе из `tools/print-agent/README.md`. Для облачного режима дополнить локальный config.json:

```json
{
  "site": "https://ВАШ_ОПУБЛИКОВАННЫЙ_САЙТ",
  "accountId": 1,
  "venueId": 1,
  "database": "state/queue.sqlite",
  "credentialFile": "state/node.dpapi",
  "printers": {
    "bar": {"name":"Бар USB","type":"windows-raw","queue":"ИМЯ ОЧЕРЕДИ WINDOWS","codePage":17,"columns":32,"cut":false},
    "kitchen": {"name":"Кухня LAN","type":"tcp","host":"192.0.2.10","port":9100,"codePage":17,"columns":42,"cut":false}
  }
}
```

Заменить все примеры. accountId/venueId взять из одноразовых данных сопряжения. `192.0.2.10` — нерабочий адрес примера. Кодировка/таблица/ширина индивидуальны для модели.

1. В интерфейсе руководителя создать код. Это отдельная операция включения будущей очереди; срок 10 минут. Старые бегунки отмечаются как история и автоматически не печатаются.
2. В подготовленном каталоге агента выполнить `node cli.mjs config.json pair`, передать показанный JSON через stdin и завершить ввод (Windows: Ctrl+Z, Enter). Не помещать токен в аргументы/переменные config/логи. Не выдавать доступ без согласования установки.
3. Агент сам генерирует случайный 256-битный ключ, сначала сохраняет DPAPI-защищённый файл, затем подтверждает сопряжение. При потере ответа повторить с тем же файлом и действующим кодом. Код не разрешает заменить уже сопряжённый узел другим ключом.
4. Запустить `node cli.mjs config.json watch` под той же учётной записью Windows. Опрос каждые 5 секунд, исходящий HTTPS, TLS проверяется, redirects запрещены. `sync` делает один проход. Служба/автозапуск сами не устанавливаются: пока окно процесса должно оставаться открытым.
5. В интерфейсе руководителя обновить данные, привязать подразделения и нажать «Тест печати». Тест отдельно подтверждается кнопкой «Отправить тест» и проходит ту же очередь. Сверить физический результат.

DPAPI CurrentUser привязывает расшифровку к профилю Windows; другой пользователь/служба не сможет автоматически прочесть ключ. Нет plaintext fallback на Linux. Файл ключа и всю SQLite-базу нужно сохранять вместе, без клонирования на второй работающий узел.

## Протокол и защита от повторов

- Существующие подтверждённые билеты заказа — исходный долговечный outbox. При первом опросе новые билеты материализуются в приватном store `__bd_print_node_v1__:<venue>`. CAS включает состояние заказов и очереди; сбой до записи не теряет исходный билет.
- Одно сопряжение принадлежит одному заведению. Сервер хранит SHA-256 хеши кода и ключа. Ключ даёт только pair/poll/start/ack печати; доступа к продажам, складу и общим store API не добавляет. Приватное состояние исключено из bootstrap; generic store-key API использует whitelist.
- Перед передачей байтов агент фиксирует локальное `sending`, затем получает одноразовое разрешение `start`. Сервер сохраняет `sending` до ответа. Повторный start не разрешает повторную отправку. Отсутствие подтверждения не освобождает задание для другого узла.
- Если ответ start потерян, байты не отправляются; локально/в облаке результат остаётся неизвестным. Это намеренная остановка для разбора, а не риск дублирования. Если потерян ack после транспорта, сохранённый локальный результат доставляется при следующем опросе без повторной печати.
- Физический endpoint замораживается локально на первой попытке. Отмена/копия наследуют его. Потеря локальной базы не допускает автоматического нового сопряжения: иначе исходный адрес и информация о состоявшейся отправке были бы потеряны.
- Отзыв ключа блокирует poll/start/ack; уже начавшуюся физическую отправку отозвать нельзя. Отзыв во время `sending` показывает неизвестный результат. Изоляция активного заведения проверяется также внутри CAS-транзакции.

## Разбор ошибок

Остановить `watch` (Ctrl+C), проверить `status`, бумагу и очередь Windows. Для доказанного отказа до передачи — `retry ID`, затем снова `watch`. Для подтверждённой бумаги — `confirm ID "Что проверено"`. Для требуемой копии после проверки — `copy ID "Причина"`, затем `watch`. Копия явно маркируется, не является слепым повтором; перед отправкой проверяется доступ узла. Исходное задание в UI отмечается как запрос копии, отдельная копия и её результат пока видны в локальном журнале агента, а не отдельной строкой облачного интерфейса.

В облачном config команды `run/import/test` отключены, чтобы обходной локальный запуск не отправил облачные задания без проверки отзыва. `test` выполняется через интерфейс руководителя. Ручной экспорт оставлен только для изолированной диагностики старого этапа.

## Явные ограничения перед эксплуатацией

- Узел один, ключ ограничен 90 днями. «Заменить компьютер» требует причину и подтверждение ручной сверки: старый ключ отзывается, все выданные ему незавершённые задания блокируются до сверки, завершённые остаются в архиве. Новый агент подключать с новым пустым каталогом состояния и новым ключом, старый журнал сохранить. Сверка с причиной и автором архивирует задание без повторной отправки. При истечении срока доставка останавливается.
- Активная очередь ограничена 100 заданиями и 400 000 байт сериализованного JSON; весь документ состояния — 1 500 000 байт. Завершённые задания атомарно переносятся в отдельные архивные записи с точным payload, маршрутом, узлом и результатом; архивные ID препятствуют повторной выдаче. Просмотр архива — по 50 записей. Переполнение откладывает новые задания в исходном POS outbox; задания свыше 200 000 байт отображаются отдельным счётчиком и требуют разбора. До явной миграции POS остаётся общий лимит старого массива 4 000 000 байт (D1 может отказать раньше). Новый нормализованный формат заказов/бегунков устраняет этот предел TEXT; процедура и ограничения описаны в docs/pos-order-journal.md. Это не обещание неограниченных ресурсов базы или чтения истории. Архив не удаляется автоматически; лимит общей базы и диска агента остаётся эксплуатационной ответственностью.
- Отмена билета, созданного до включения облачной очереди, получает `blocked_history`: старую физическую доставку нельзя достоверно восстановить. Требуется ручной разбор. Старые билеты без принтера не переназначаются автоматически.
- Нет полного offline-POS, автоматического обнаружения Windows-очередей/моделей, GUI-установщика, Windows-службы, мониторинга бумаги/отсечки на всех устройствах. Принтеры сначала описываются в локальном config; руководитель выбирает их в PWA.
- Настоящие Windows DPAPI, PowerShell/C# Winspool и USB/LAN модели в этой Linux-среде не проверены. Обязательны согласованные проверки на Windows и хотя бы одной USB и одной LAN модели, включая потери питания/сети, кириллицу, cutter, остановку spooler и восстановление.

Microsoft DPAPI reference: https://learn.microsoft.com/en-us/dotnet/api/system.security.cryptography.protecteddata
Проверенные подходы конкурентов и транспортные границы: `docs/printer-transport-proposal.md`.

При потере локальной базы отмена без сохранённого физического адреса исходной отправки блокируется как неизвестный результат: текущая привязка принтера не подставляется.
