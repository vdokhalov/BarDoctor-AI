# BarDoctor Print Agent

**Не устанавливался на компьютер заведения. Не опубликован.** Текущий автоматический режим, сопряжение, отзыв и интерфейс руководителя описаны в `docs/print-cloud-stage2.md` (от корня репозитория). Ниже сохранена инструкция локального диагностического режима первого этапа. Ручной импорт не является обычным рабочим процессом облачного режима. Реальные постоянные ключи в ходе разработки не создавались.

## Что поддерживает эта версия

- Один Windows-компьютер и одна локальная SQLite-база на заведение.
- Сетевой ESC/POS по TCP с явно настроенным IP/портом.
- USB через существующую Windows-очередь совместимого ESC/POS-принтера, Winspool `RAW`. Драйвер/очередь должны пропускать ESC/POS без преобразования. Обычные GDI-only, офисные и фискальные принтеры не заявлены.
- Кириллица CP866, 32/42/48 символов; номер таблицы ESC `t` нужно сверить с руководством конкретной модели. Пример `17` не универсален. Другие символы блокируют задание до отправки, а не превращаются в мусор. Отрезчик по умолчанию выключен.
- Задания подтверждения/отмены берут логический printerId и раздел из исходного бегунка BarDoctor. Официант подразделение не выбирает. Отмена и копия сохраняют и исходный локальный транспортный адрес после первой попытки отправки.

## Подготовка и запуск после отдельного разрешения на установку

1. На согласованном Windows-компьютере установить поддерживаемый Node.js 24.x, а для USB — драйвер производителя и локальную очередь. PowerShell должен разрешать запуск локального `spool.ps1` по существующей политике. Пакет не изменяет ExecutionPolicy, firewall, службы или автозапуск; если политика запрещает скрипт, остановиться и согласовать с администратором.
2. Скопировать каталог `tools/print-agent` в каталог приложения. Скопировать `config.example.json` как `config.json`, указать реальный `venueId`, точное имя системной очереди или IP/порт, профиль модели. `192.0.2.10` — нерабочий адрес примера. Ключи `kitchen`/`bar` должны совпадать с логическими printerId маршрутизации BarDoctor; это не имена разделов. Настройку делает руководитель/администратор.
3. SQLite хранить на локальном диске в каталоге, доступном только учётной записи оператора. Не использовать сетевую папку, OneDrive или одновременно несколько компьютеров. Скопированная/утраченная база теряет защиту от повторного импорта: не создавать пустую базу для повторной отправки старых экспортов. Для переноса остановить агент и сохранить весь каталог `state`, включая журнал, до повторного запуска.
4. Добавить тестовый бегунок и отдельно разрешить его отправку:

```powershell
node cli.mjs config.json test kitchen
node cli.mjs config.json status
node cli.mjs config.json run
```

Команда `test` только ставит задание в очередь. `run` отправляет все доступные pending-задания, не только тест. На первом запуске база должна содержать только согласованные тесты. Сверить бумагу, кириллицу, ширину, количество, заголовок. Только если бумага действительно проверена:

```powershell
node cli.mjs config.json confirm "test:ID_ИЗ_ВЫВОДА" "Бегунок получен и прочитан"
```

## Диагностический экспорт/импорт (не обычный облачный процесс)

Новый **неопубликованный** GET `/api/pos-preparation/export?orderId=...` использует существующую авторизацию BarDoctor и выбранное заведение. Доступен руководителю с `sales.create`; возвращает только бегунки одного явно указанного заказа, без рецептов/себестоимости. Это технический API первого этапа, кнопки экспорта в PWA пока нет. Он проверен в изолированном route runtime. Для локального стенда вызвать его через штатный авторизованный API-клиент и сохранить JSON; не вытаскивать токены в команды/логи. Production v544 этого endpoint ещё не содержит.

Оператор импортирует полученный проверенный файл:

```powershell
node cli.mjs config.json import bardoctor-tickets.json
node cli.mjs config.json status
node cli.mjs config.json run
```

Файл не имеет криптографической подписи. В этом этапе локальная учётная запись и ручной выбор файла — граница доверия; не импортировать посторонние файлы. Агент игнорирует дополнительные поля, валидирует данные и не принимает адрес устройства/код/команды из файла. Один ID с другим содержимым отклоняется, весь такой импорт откатывается. Повтор того же экспорта ничего не печатает повторно. Экспорт после отмены добавляет только новый бегунок отмены.

`run` — конечный проход очереди, не Windows-служба. После перезапуска снова выполнить `status`, затем `run`; задания `sending` восстановятся как `outcome_unknown` и сами не уйдут повторно. SQLite-блокировка не допускает второй процесс, снимается ОС после завершения/аварии. Пока один принтер требует разбора, другой может продолжить.

## Что означают состояния

| Состояние | Значение / действие |
|---|---|
| pending | Ожидает явного `run` |
| unconfigured | У исходного бегунка не было printerId; поздняя настройка не подменяет исторический маршрут. Нужен разбор руководителем, автоматической переназначающей команды нет |
| sending | Отправка начата, состояние записано до обращения к устройству |
| accepted_by_transport | TCP завершил запись или spooler принял документ. **Бумага не подтверждена** |
| failed_before_send | Доказанный отказ до передачи: настройка, кодировка, невозможность соединения/старта процесса |
| outcome_unknown | Отправка могла произойти. Проверить бумагу и очередь Windows; не повторять вслепую |
| operator_confirmed | Оператор явно сообщил, что видел распечатку |
| operator_resolved | Оператор явно запросил копию; исходный физический результат по-прежнему не утверждается |

Для доказанного отказа до передачи — исправить причину, затем `retry ID` и отдельно `run`. Замороженный адрес после первой попытки остаётся прежним: смена адреса уже отправляемого задания не поддерживается.

Для неизвестного результата проверить бумагу и spooler. Если оригинал найден — `confirm ID "Найден оригинал"`. Если после проверки нужна копия:

```powershell
node cli.mjs config.json copy "prep:ID" "Проверены бумага и spooler; нужна копия"
node cli.mjs config.json run
```

Копия имеет отдельный ID в журнале, на бумаге обязательный заголовок **КОПИЯ**. Она идёт перед ожидающими отменами этого оригинала. Первый этап допускает одну явную копию оригинала; повторные копии копий требуют ручного разбора и не поддерживаются. Windows spooler может самостоятельно возобновить уже принятое задание после появления бумаги: до копии нужно проверить его очередь, иначе возможны две физические распечатки. Пакет не обещает exactly-once физическую печать.

## Проверки и границы

Тесты: `node --test tests/print-agent.test.mjs` из корня репозитория; route: `node --import tsx --test tests/print-ticket-export.test.ts`.

Проверены имитации: TCP приём байтов локальным сервером, протокол вызова Windows-процесса, журнал SQLite, дедупликация, конфликт ID, отмена, копия, перезапуск, неизвестный исход, блокировка второй копии процесса, независимость принтеров, export permissions/venue isolation/read-only. Модель поведения Winspool имитирована; C# P/Invoke ещё не запускался на Windows.

Облачная очередь, сопряжение/отзыв, экран руководителя и тест из UI добавлены в этапе 2; ограничения перечислены в docs/print-cloud-stage2.md. Выбор физической очереди/профиля пока задаётся локальным config. До production — реальная матрица хотя бы одной USB и одной LAN модели, кириллица, бумага, cutter, отключение кабеля/питания, остановка spooler, рестарт Windows, повторное подключение. Облачная очередь не делает POS полностью автономным без интернета.

Основание RAW-адаптера: Microsoft StartDocPrinter / WritePrinter / EndDocPrinter:
https://learn.microsoft.com/en-us/windows/win32/printdocs/startdocprinter
https://learn.microsoft.com/en-us/windows/win32/printdocs/writeprinter

Исследование Poster/r_keeper/iiko и будущая архитектура: `docs/printer-transport-proposal.md`. Их подход с локальным узлом адаптирован; универсальная совместимость не заявляется.
